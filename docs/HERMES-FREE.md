# Hermes Free — اجرای Hermes Agent روی چت رایگان دیپ‌سیک

**Hermes Free** گزینه‌ای در RC است که [Hermes Agent](https://github.com/NousResearch/hermes-agent) (ایجنت متن‌باز Nous Research) را به‌جای API پولی دیپ‌سیک، روی **چت وب رایگان دیپ‌سیک** اجرا می‌کند؛ با همان توکنی که provider همیشگی RC استفاده می‌کند. نه کلید API لازم است، نه هزینه.

---

## ۱. مسئله: دو دنیای ناسازگار

| | Hermes (کلاینت) | چت وب دیپ‌سیک (`rc serve`) |
|---|---|---|
| مدل ارتباط | **بی‌حالت** (OpenAI Chat Completions): هر درخواست کل تاریخچه + همهٔ ابزارها را دوباره می‌فرستد | **با‌حالت**: یک نشست که فقط پیام جدید می‌گیرد |
| فراخوانی ابزار | function calling بومی با JSON Schema | وجود ندارد؛ فقط متن |
| system prompt | پیام `system` در هر درخواست | ندارد |

اتصال ساده و مستقیم این دو، چهار مشکل جدی دارد که همه را در `rc serve` فعلی بررسی و تأیید کردیم:

1. `rc serve` فقط **آخرین پیام** را به مدل می‌دهد؛ پس system prompt هرمس (شخصیت، حافظه، مهارت‌ها) **گم می‌شود** و از نتایج ابزارهای موازی فقط آخری می‌رسد.
2. همهٔ درخواست‌ها در **یک نشست سراسری** می‌روند؛ گفتگوهای جدا با هم **قاطی می‌شوند**.
3. `rc serve` system prompt و **ابزارهای خودش** را هم تزریق می‌کند که با ابزارهای هرمس تداخل دارد.
4. هر فراخوانی ابزار ناقص یا اشتباه فقط **خطای ۵۰۰** برمی‌گرداند و حلقهٔ ایجنت می‌شکند.

## ۲. معماری

```
Hermes Agent CLI
     │  OpenAI API  (DEEPSEEK_BASE_URL = gateway، کلید تصادفی هر اجرا)
     ▼
┌──────────────────────── Hermes Free Gateway (درون افزونه، 127.0.0.1) ───────────────────────┐
│  Delta Sync ── Compact Tool Manifest ── Schema-aware Parser ── Self-Repair ── Guard ── Telemetry │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
     │  POST /rc/raw/turn  (نشست صریح، بدون prompt و ابزار سرور)
     ▼
rc serve (CLI داخل افزونه)  ──▶  chat.deepseek.com  (توکن وب رایگان)
```

| فایل | نقش |
|---|---|
| `src/hermes/freeProtocol.ts` | منطق خالص پروتکل (بدون شبکه و VS Code؛ تست‌پذیر) |
| `src/hermes/freeGateway.ts` | سرور HTTP سازگار با OpenAI، حلقهٔ ترمیم، استریم، تله‌متری |
| `src/hermes/free.ts` | مدیریت در VS Code: راه‌اندازی `rc serve`، بررسی نسخه، کانال Output |
| `cli-overlay/server/{index,session}.js` | endpoint جدید `/rc/raw/turn` در `rc serve` |
| `scripts/test-hermes-free.mjs` | ۱۶ تست (پروتکل + سرور سرتاسری با مدل شبیه‌سازی‌شده) |

## ۳. نوآوری‌ها

### ۱) Delta Sync — تبدیل API بی‌حالت به نشست با‌حالت

هر گفتگو به یک **زنجیرهٔ هش** تبدیل می‌شود: `chain[i] = sha1(chain[i-1] + canonical(message[i]))`.
وقتی درخواست بعدی هرمس می‌رسد، gateway دنبال گفتگویی می‌گردد که زنجیره‌اش **پیشوند دقیق** این درخواست باشد. اگر پیدا شد، **فقط پیام‌های جدید** (مثلاً نتیجهٔ ابزار) به همان نشست وب فرستاده می‌شود.

- شکل canonical، شناسهٔ tool-call و ترتیب کلیدهای JSON را نادیده می‌گیرد؛ پس بازنویسی آن‌ها توسط کلاینت تطبیق را خراب نمی‌کند.
- system prompt جدا ردیابی می‌شود؛ اگر هرمس آن را عوض کند، فقط نسخهٔ جدید ارسال می‌شود.
- اگر تطبیق پیدا نشود (مثلاً هرمس context را فشرده کرده باشد)، یک نشست تازه با کل context ساخته می‌شود؛ یعنی **درستی همیشه حفظ می‌شود** و فقط سرعت کم می‌شود.
- اگر delta شکست بخورد، آن گفتگو کنار گذاشته می‌شود تا خطا روی خطا انباشته نشود.

### ۲) Compact Tool Manifest

اسکیمای JSON هر ابزار به یک امضای یک‌خطی تبدیل می‌شود:

```
read_file(path: string, offset?: int, limit?: int)
  Read a file from the workspace.
terminal(command: string, background?: boolean, mode?: "fast" | "safe")
```

این امضاها **فقط یک بار** در هر نشست فرستاده می‌شوند. اگر مجموعهٔ ابزارها تغییر کند، فقط یک **diff** (اضافه‌شده/حذف‌شده) می‌رود.

### ۳) Parser آگاه از اسکیما

مقادیر آرگومان‌ها **بر اساس نوع اعلام‌شده در اسکیما** تبدیل می‌شوند: `"123"` برای پارامتر string همان رشته می‌ماند، ولی برای integer به عدد تبدیل می‌شود. پارسر قبلی `rc serve` همه‌چیز را `JSON.parse` می‌کرد و مسیر فایلی مثل `123` را به عدد تبدیل می‌کرد.
کد چندخطی با تورفتگی دست‌نخورده منتقل می‌شود. پارامترهای اجباری، enumها و ابزارهای ناشناخته بررسی می‌شوند. لغزش‌های جزئی مثل `Read-File` به‌جای `read_file` خودکار اصلاح می‌شوند. اگر مدل فراخوانی را به شکل JSON نوشته باشد، بازیابی می‌شود.

### ۴) Self-Repair — ترمیم خودکار درون همان نشست

اگر فراخوانی ابزار نامعتبر باشد، gateway به‌جای برگرداندن خطا، **پیام دقیق خطا** را (مثلاً `missing required parameter "path"` یا `Did you mean "terminal"?`) همراه امضای درست به همان نشست می‌فرستد و از مدل می‌خواهد اصلاحش کند (پیش‌فرض تا ۲ بار، قابل تنظیم با `rc.hermesFree.maxRepairs`). هرمس فقط نتیجهٔ سالم را می‌بیند.

### ۵) Hallucination Guard

مدل‌های بدون function calling بومی گاهی بعد از فراخوانی ابزار، **نتیجه را خودشان حدس می‌زنند**. gateway هر چیزی را که بعد از آخرین `</function_call>` آمده، یا هر `<tool_result>` ساختگی را حذف می‌کند تا هرمس همیشه ابزار واقعی را اجرا کند.

### ۵.۵) فهم فرمت بومی DSML دیپ‌سیک

در تست واقعی با هرمس دیدیم که مدل دیپ‌سیک گاهی پروتکل ما را نادیده می‌گیرد و فراخوانی ابزار را با **فرمت داخلی خودش (DSML)** می‌نویسد:

```
<｜｜DSML｜｜ invoke name="read_file">
<｜｜DSML｜｜ parameter name="path" string="true">package.json</｜｜DSML｜｜ parameter>
</｜｜DSML｜｜ invoke>
```

یک پل ساده این را متن معمولی حساب می‌کند و markup خام به‌عنوان «جواب» به کاربر می‌رسد. پارسر gateway این فرمت را با همهٔ حالت‌هایش (یک یا دو خط عمودی، فاصله، ویژگی `string`) به فراخوانی ابزار واقعی تبدیل می‌کند.

### ۶) امنیت و ایزوله‌سازی

- gateway فقط روی `127.0.0.1` و پورت تصادفی گوش می‌دهد و **کلید تصادفی همان اجرا** را می‌خواهد؛ پس پروسه‌های دیگر سیستم نمی‌توانند از توکن شما استفاده کنند.
- endpoint خام `rc serve`، نشست سراسری خودش را قبل و بعد از هر نوبت **ذخیره و بازیابی** می‌کند؛ پس Hermes Free با Velocity و provider همیشگی RC تداخل ندارد.
- قطع شدن هرمس (Stop یا Ctrl+C) زنجیره‌وار تولید پاسخ در دیپ‌سیک را هم متوقف می‌کند.

### ۷) تله‌متری زنده

در چت، برای هر فراخوانی مدل یک خط نشان داده می‌شود:

```
Hermes Free · ⚡ delta sync · sent 137 B · saved 85% · 2.4s
Σ Hermes Free · 2 model call(s), 1 via delta sync · sent 1.3 KB instead of 1.5 KB
```

دستور **RC: Hermes Free Gateway Stats** آمار کل جلسه را نشان می‌دهد و کانال Output با نام «RC Hermes Free» لاگ دقیق دارد.

## ۴. نتایج اندازه‌گیری‌شده

**تست واقعی** روی چت وب رایگان دیپ‌سیک (حلقهٔ دو مرحله‌ای ایجنت: فراخوانی `read_file` و سپس پاسخ با نتیجه):

| نوبت | حالت | ارسال‌شده | بازپخش ساده | نتیجه |
|---|---|---|---|---|
| ۱ | نشست جدید | 1221 کاراکتر | 645 | فراخوانی درست `read_file({"path":"notes.txt","limit":50})`؛ `limit` به عدد تبدیل شد |
| ۲ | **delta** | **137 کاراکتر** | 900 | پاسخ درست، در **همان نشست** |

**تست واقعی با Hermes Agent v0.21.5 داخل Docker** (۵۸ مهارت و همهٔ ابزارهای هرمس):

| سناریو | نتیجه |
|---|---|
| اجرای `python3 -c "print(17*23)"` با ابزار terminal هرمس | جواب درست `391`؛ نوبت delta فقط **۱۵۲ کاراکتر** به‌جای **۶۸ KB** (۹۹.۸٪ کمتر) |
| خواندن `package.json` از پروژهٔ mount‌شده | جواب درست `rc-vscode` / `0.3.0`؛ فراخوانی DSML بومی بازیابی شد |

صرفه‌جویی با طول گفتگو بیشتر می‌شود: بازپخش ساده با هر نوبت بزرگ‌تر می‌شود، ولی delta تقریباً ثابت می‌ماند. در تست خودکار با یک system prompt واقعی‌اندازه، نوبت سوم **بیش از ۱۰ برابر** کوچک‌تر از بازپخش ساده بود. (در نوبت اول، متن پروتکل کمی سربار دارد.)

اجرای تست‌ها:

```bash
npm run test:hermes-free
```

## ۵. استفاده

1. Hermes Agent را نصب کنید ([راهنما](https://github.com/NousResearch/hermes-agent#installation)).
2. توکن وب دیپ‌سیک را با `/token` تنظیم کنید (همان توکن provider همیشگی RC).
3. در چت، provider را روی **Hermes Free** بگذارید (از منوی بالای چت یا با `/provider`).

تنظیمات: `rc.hermesFree.model` (`deepseek-chat` یا `deepseek-reasoner` برای DeepThink) و `rc.hermesFree.maxRepairs`. دستورها: **RC: Hermes Free Settings** و **RC: Hermes Free Gateway Stats**.

### اجرای هرمس داخل Docker

اگر هرمس به‌جای نصب محلی در کانتینر اجرا شود (مثلاً با image رسمی `nousresearch/hermes-agent`)، RC آن را خودکار پیدا می‌کند (`rc.hermes.docker.container` = `"auto"`) یا می‌توانید اسم کانتینر را مستقیم بدهید. نوبت‌ها با `docker exec` اجرا می‌شوند:

- کلیدها فقط با نام متغیر (`-e NAME`) فرستاده می‌شوند و در خط فرمان دیده نمی‌شوند.
- آدرس `127.0.0.1` gateway خودکار به `host.docker.internal` تبدیل می‌شود؛ Docker Desktop آن را به loopback میزبان می‌رساند، پس gateway لازم نیست روی شبکه باز شود.
- مسیر پروژهٔ ویندوز با `rc.hermes.docker.pathMappings` به مسیر داخل کانتینر ترجمه می‌شود؛ مثلاً `{ "C:\\codes": "/workspace" }` برای mount `C:/codes:/workspace`.
- چون کشتن `docker exec` پروسهٔ داخل کانتینر را نمی‌کشد، PID هرمس ثبت می‌شود و Stop آن را واقعاً متوقف می‌کند.

### کارت‌های ابزار

هر فراخوانی ابزار هرمس در چت یک کارت جدا دارد: آیکن، نام ابزار، آرگومان اصلی (فایل، دستور یا الگو) و وضعیت در سمت راست. کارت اول «در حال اجرا» (`…`) است و وقتی نتیجه برسد همان کارت به‌روز می‌شود: `✓`، `✗ exit 1`، `✓ 7 passed`، `✓ 41 lines`، یا `🔧 repaired` برای فراخوانی‌ای که gateway ترمیمش کرده. وضعیت‌ها از خروجی JSON واقعی ابزارهای هرمس خوانده می‌شوند (`src/hermes/toolCards.ts`)، و خلاصهٔ نوبت هم در پایان کارت‌ها می‌ماند.

### منبع مدل: دیپ‌سیک رایگان یا لینک دلخواه

در **RC: Hermes Free Settings ← Model source** دو گزینه هست:

| منبع | توضیح |
|---|---|
| دیپ‌سیک رایگان (پیش‌فرض) | چت وب با توکن رایگان؛ همراه با Delta Sync و ترمیم خودکار |
| لینک دلخواه | هر API سازگار با OpenAI، مثل `http://localhost:11434/v1` (Ollama)، vLLM، LM Studio یا سرور خودتان، با نام مدل و کلید اختیاری |

هرمس لینک دلخواه را مستقیم قبول نمی‌کند: `OPENAI_BASE_URL` را نادیده می‌گیرد و برای مدل‌های ناشناخته به مدل تنظیمات خودش برمی‌گردد. برای همین هرمس همیشه با gateway حرف می‌زند و gateway درخواست را **با نام مدل واقعی و فراخوانی ابزار بومی** به لینک شما می‌فرستد. تنظیمات هرمس دست نمی‌خورد و کارت‌ها هم کار می‌کنند. کلید در keychain سیستم‌عامل ذخیره می‌شود.

### هرمسِ روی سرور (Hermes Server)

ارائه‌دهندهٔ **Hermes (server)** به هرمسی وصل می‌شود که روی سرور دیگری اجرا می‌شود و API آن روشن است (`API_SERVER_ENABLED=true`). فقط آدرس (مثلاً `https://my-server.com:8642`) و `API_SERVER_KEY` لازم است. هنگام ذخیره، اتصال و کلید با `/v1/capabilities` بررسی می‌شوند.

- هر چت یک **session روی سرور** دارد (`/api/sessions/{id}/chat/stream`)؛ گفتگو سمت سرور ادامه پیدا می‌کند و لازم نیست کل تاریخچه دوباره فرستاده شود.
- رویدادهای زندهٔ `tool.started` و `tool.completed` به همان کارت‌های ابزار تبدیل می‌شوند.
- **تأیید دستورهای حساس:** در حالت دسترسی کامل خودکار «یک بار» تأیید می‌شود؛ در غیر این صورت VS Code می‌پرسد (یک بار، برای این session، همیشه، یا رد).
- دکمهٔ Stop، اجرا را روی خود سرور متوقف می‌کند (`/v1/runs/{id}/stop`).
- ابزارها **روی سرور و روی فایل‌های سرور** اجرا می‌شوند، نه روی پروژهٔ کامپیوتر شما. مدل هم همانی است که روی سرور تنظیم شده.

### لینوکس

- **Docker روی لینوکس:** `host.docker.internal` فقط در Docker Desktop وجود دارد. روی Docker Engine، gateway علاوه بر `127.0.0.1` روی آدرس gateway شبکهٔ کانتینر (مثلاً `172.18.0.1`) هم گوش می‌دهد، با همان کلید تصادفی. کانتینری که روی شبکهٔ host است مستقیم از `127.0.0.1` استفاده می‌کند، و Docker Desktop for Linux مثل ویندوز رفتار می‌کند.
- **Stop:** هرمس محلی در گروه پروسهٔ خودش اجرا می‌شود و Stop کل گروه را می‌کشد، پس زیرپروسه‌ها هم متوقف می‌شوند.
- **مسیرها:** روی لینوکس به حروف بزرگ و کوچک حساس‌اند، روی ویندوز نه.
- **Node:** نسخهٔ لینوکس داخل VSIX هست و مجوز اجرایش هنگام اجرا تنظیم می‌شود.

همهٔ تست‌ها (`npm run test:hermes-free`) هم روی ویندوز و هم روی لینوکس واقعی پاس می‌شوند.

**تست‌های واقعی این بخش:**

| سناریو | نتیجه |
|---|---|
| Hermes Server روی API واقعی هرمس | کارت `terminal` از `…` به `✓`، جواب `remote-mode-ok`؛ در پیام دوم همان session، نتیجهٔ پیام اول یادش بود |
| لینک دلخواه (Ollama، `qwen3.5-hermes`) | Hermes در Docker ← gateway ← Ollama؛ فراخوانی ابزار بومی و جواب درست |
| لینوکس | gateway و Hermes محلی روی لینوکس با لینک دلخواه: جواب `Linux`؛ Stop وسط اجرا: ۰ پروسهٔ باقی‌مانده |

## ۶. محدودیت‌ها

- چت وب دیپ‌سیک یک API رسمی برای برنامه‌ها نیست؛ ممکن است با تغییرات سایت از کار بیفتد، و استفادهٔ خودکار ممکن است با قوانین استفادهٔ دیپ‌سیک سازگار نباشد.
- درخواست‌ها در `rc serve` صف می‌شوند؛ پس فراخوانی‌های موازی هرمس پشت سر هم اجرا می‌شوند.
- هر نشست وب همهٔ تاریخچه‌اش را نگه می‌دارد؛ برای کارهای خیلی طولانی، فشرده‌سازی context خود هرمس باعث ساخت نشست تازه می‌شود (کار درست انجام می‌شود، فقط یک نوبت کندتر).
- تصاویر پشتیبانی نمی‌شوند؛ فقط متن به مدل می‌رسد.
